# 根因分析大模型请求组装实现说明

> 用途：解释根因分析时，提示词、系统架构图谱、日志证据、算法候选和会话配置如何组合成一次模型请求，以及返回值如何被校验、保存。
> 核对日期：2026-09-03。代码基线：`main`，HEAD `8462309` **加当前工作区未提交修改**，不是仅以该提交为准。
> 范围：当前项目上传日志后的 RCA 主链路；不把历史方案、其他分支或远程模型服务内部实现当作已实现行为。
> 本文只记录实现，不修改业务代码；所有 IP、工号和示例日志均为虚构演示数据，不引用实际部署凭据。

## 1. 先看结论

模型收到的不是原始 ZIP，也不是浏览器上绘制出来的图，而是后端构造的一段字符串：

```text
HTTP JSON 请求体
├─ content：固定 RCA 指令 + 决策约束 + 返回 JSON 格式 + “输入数据：” + 紧凑 JSON
│  ├─ architecture_graph：本次读取到的项目静态架构，节点/关系使用紧凑数组
│  ├─ architecture_focus：候选节点及一跳邻居的有限描述补充
│  ├─ incident：单个故障的候选原因、关键证据、故障时间、日志实体、压缩日志
│  └─ algorithm_candidates：确定性 RCA 引擎提供的辅助候选
├─ assistant_prompt：配置提供的独立字段，不是上面固定 RCA 指令的替代品
├─ model_config_id / assistant_role / assistant_name / 其他配置
└─ conversation_id：本批次已有返回会话 ID 时才携带
```

关键事实：

1. 一个批次可形成多个故障，通常每个故障调用一次模型，不是把整批所有故障拼成一次调用。
2. 每次调用都重新放入完整紧凑架构，**没有“首次发全图、后续只发指纹”的分支**。
3. 同一批次复用一个 `RcaDecisionService` 的会话 ID；新批次新建服务对象，首次不传会话 ID。
4. 当前 `_import_details()` 用普通 `for` 顺序处理模型调用，不是同一批次并行调用。外层 `run_in_threadpool` 是把同步任务移出事件循环，不代表内部故障并行。
5. 日志先进行确定性筛选/压缩，图谱保留本次架构快照中的有效实体和关系；没有使用 embedding 向量检索或另一个模型做日志摘要。
6. `possible_member_nodes` 等集群待排查实例字段由服务端根据真实成员关系展开，**不是直接要求模型返回一份任意实例清单**。

## 3. 从日志上传到请求的调用顺序

### 3.1 接收文件和工号

入口是 `POST /api/projects/{project_id}/logs/analyze`，由 `analyze_project_logs()` 处理。

1. `require_user` 得到登录用户；`_project_for_user()` 校验项目访问权限。
2. 从 `user["employee_id"]` 读取并 `strip()` 工号。为空则返回 HTTP 400，不启动任务。
3. 保存上传文件和可选训练文件，创建批次 UUID 与 SQLite 批次记录。
4. 使用 `asyncio.create_task(_run_log_analysis_task(...))` 启动后台任务，接口立即返回 HTTP 202。
5. 工号作为独立 Python 参数传入后台任务，不是从日志、图谱或模型输出中取得。

落盘目录由 `_data_dir()` 构造：

```text
<APP_DATA_ROOT>/projects/<project_id>/logs/<batch_id>/
├─ <清理后的上传文件名>
├─ <可选训练文件名>
└─ output/
```

### 3.2 日志算法产生 `detail`

`_run_log_analysis_task()` 先调用：

```python
runner = LogFaultRunner()
summary = await run_in_threadpool(runner._run_pipeline, input_path, output_dir, train_path)
```

`_run_pipeline()` 导入外部 `logfault.pipeline`，执行：

```python
run_pipeline(
    input_path=input_path,
    output_dir=output_dir,
    config_path=config_path,
    train_input=train_path,
)
```

外部算法路径来自 `LOGFAULT_PROJECT_PATH`，未指定时尝试相邻的 `LogFaultAlgorithm`。该包的具体版本决定解析、窗口和异常段挖掘细节；本文说明本仓库如何消费其结果，不假定外部包内部实现不变。

随后创建项目隔离客户端与集成器：

```python
scoped = ProjectScopedGraphClient(project_id)
imported = await run_in_threadpool(
    IncidentGraphIntegrator(scoped, employee_id=employee_id).import_path,
    output_dir,
    input_path.name,
    batch_id[:12],
)
```

`import_path()` 的输入解析优先级：

| 来源 | 转换函数 | 结果 |
|---|---|---|
| `incident_details.json`，或直接输入的 JSON 文件 | `import_path()` 内解析 | JSON 对象转为一项列表，数组保留其中的字典项 |
| 没有有效详情但有 `incidents.csv` | `_details_from_incidents_csv()` | 每行形成最小故障详情；`timeline/root_candidates/upstream_effects` 为空 |
| 上述都没有有效详情，但有 `events.csv` | `_details_from_events_csv()` | 取 `level == ERROR` 的事件；以首个 ERROR 为根线索生成一个补偿故障 |

`events.csv` 补偿分支：有首个 ERROR 的非空 trace 时，优先取同 trace 的全部事件；否则取前 50 条 ERROR。没有 ERROR 则不生成补偿详情。该限制发生在进入模型压缩器之前。

有 `incident_prefix` 时，给模型及 HugeGraph 使用的故障 ID 加批次前缀，例如 `abcd12345678:I00001`；`source_incident_id` 保存原编号。`IncidentImportResult.incident_details` 保留加前缀前的详情，用于后续 SQLite 持久化对齐。

### 3.3 读取架构、准备算法候选、逐个决策

`IncidentGraphIntegrator._import_details()` 的实际顺序：

```python
architecture = self.db.read_architecture_graph(limit=5000)
rca_engine = RootCauseEngine(architecture)
top_k = max(1, min(self.settings.rca_top_k, 20))

# 先完成本批次各故障的确定性分析。
prepared = []
for index, detail in enumerate(details):
    rca = rca_engine.analyze(detail, top_k=top_k)
    prepared.append({"index": index, "detail": detail, "rca": rca, "data": rca.model_dump()})

# 再逐故障调用模型，然后写对应的动态图数据。
for item in prepared:
    decision = self.decision_service.enrich(item["detail"], item["data"], architecture)
    # 实际代码随后执行 _begin_graph_buffer / _import_one / _flush_graph_buffer。
```

同一批次使用同一份 `architecture` 快照，即使处理前一个故障时写入了动态图，后一个故障的提示词也不会把那些新写入的动态节点当成架构重新读取。处理期间用户修改架构，也不会自动替换这份批次内快照。

### 3.4 一次 `enrich()` 的输入输出

| 参数/结果 | 类型 | 含义 |
|---|---|---|
| `detail` | `dict` | 单个故障的算法详情、候选原因日志、时间线 |
| `analysis` | `dict` | `RootCauseAnalysis.model_dump()`，算法根因候选及限制 |
| `architecture` | `GraphResponse` 或图谱字典 | 项目静态架构快照 |
| 返回值 | `dict` | 标准化模型决策，或算法兜底决策；包含 `source` 和诊断信息 |

`enrich()` 先准备可落在架构上的算法兜底，再检查模型开关。启用时调用 `_build_prompt_with_meta()` → `_post_conversation()` → `_parse_model_json()` → `_normalize_model_result()`；这几个步骤在 `try` 内，异常会返回兜底。初始兜底构造在 `try` 外，不能把它理解为所有输入错误都绝不会向外抛出。

## 4. 图谱如何变成 `architecture_graph`

### 4.1 项目隔离与“完整图”的边界

`ProjectScopedGraphClient.read_graph()` 从 HugeGraph 读取快照后，只保留名称带 `project::<project_id>::` 前缀或 `meta.project_id` 属于当前项目的节点；边的两端都必须被保留。

节点名称通过 `meta.display_name` 或去掉项目前缀得到。返回给模型的 `GraphNode.id` 被设为该显示名，**不是 HugeGraph 原生顶点 ID**。后续写入原生图数据库时，必须再按名称解析真实 ID，不能直接拿模型 ID 当数据库 ID。

`read_architecture_graph()` 进一步过滤：

- `kind` 属于 `Incident/Trace/LogEvent/Exception/Window/Metric/RCAHypothesis/UnresolvedDependency` 的节点。
- `meta.dynamic_observation` 为真的节点。
- `meta` 含 `raw_service`，且描述恰好为“异常链路关联到的服务”的历史动态服务节点。
- 任何端点已被上述规则排除的关系。

这里的“完整架构”表示**本次已经读取并通过静态过滤的快照全部参与组装**，不是无限读取整个数据库：当前 RCA 传入 `limit=5000`，项目客户端扩大为 `min(max(limit * 10, 5000), 50000)`，即全局最多读 50,000 个节点；底层 `read_graph()` 读取最多两倍数量的关系，即 100,000 条，然后再按项目过滤。这不是分页穷尽读取。超过全局读取上限、静态类型标错、动态标识标错，都可能让节点进不了提示词。

### 4.2 `_architecture_catalog()` 标准化

输入 `GraphResponse` 或 `{nodes: [...], edges: [...]}`，输出内部目录：

```text
catalog = {
  nodes: [{node_id, name, aliases, kind, type, description, runtime}, ...],
  edges: [{source_node_id, target_node_id, type, relation, description, runtime}, ...],
  by_id: node_id → 节点,
  alias_to_id: 规范化标识 → node_id,
  adjacency: node_id → 无向相邻节点集合
}
```

处理规则：

- `node_id = data.id or name`；名称、ID 为空或 ID 重复的节点跳过。
- 关系端点优先由节点名称转换为 ID；任一端不存在、或两端相同的自环被跳过。
- `kind` 默认 `Component`；关系 `type` 默认 `CALLS` 并转大写。
- `alias_to_id` 使用 ID、名称、别名、主机名、IP、端点、实例标识、服务名、Pod 标识，经 `strip().casefold()` 建索引。同标识冲突时 `setdefault()` 保留先出现的节点，不能理解成语义消歧。
- `adjacency` 同时加入两个方向，供后面的传播路径连通性校验使用；原始关系方向仍保留在 `edges`。
- 节点描述先做空白归一和简单敏感键值遮盖，最多 240 字符；关系描述最多 160 字符。

### 4.3 元数据白名单与字段压缩

不是把整个 `meta` 原样发给模型，而是 `_safe_runtime_meta()` 抽取顶层已知字段，随后 `_compact_runtime()` 改成短键。

| 模型短键 | 内部规范字段 | 接受的原始 `meta` 键 |
|---|---|---|
| `a` | aliases | aliases、alias、raw_service |
| `h` | hostnames | host、hosts、hostname、hostnames |
| `ip` | ips | ip、ips、ip_address、ip_addresses |
| `p` | ports | port、ports、service_port、target_port、container_port |
| `ep` | endpoints | endpoint、endpoints、address、addresses |
| `ins` | instance_ids | instance、instance_id、instanceId、instance_ids |
| `svc` | service_names | service、service_name、serviceName、application_name |
| `cl` | clusters | cluster、cluster_name、clusterName |
| `ns` | namespaces | namespace、namespaces |
| `pod` | pods | pod、pod_name、podName、pods |
| `pr` | protocols | protocol、protocols、scheme |
| `rg` | regions | region、regions |
| `z` | zones | zone、availability_zone、zones |
| `hc` | health_checks | health_check、health_check_url、health_url、probe |

注意规范字段与输入别名并不完全等同，例如当前输入白名单中没有顶层 `service_names`、`clusters`、`health_checks` 这几个复数键，不能因输出名称如此就假定输入也支持。排查缺字段时应按第三列核对。

具体筛选：

1. 列表/元组/集合递归展开，字典直接忽略；不会主动展开 `meta.runtime.ip` 一类嵌套结构。
2. 每个规范字段大小写不敏感去重，最多保留前 8 项；值最终以数组发送，单个端口也是 `[6379]`。
3. IP 必须通过 `ipaddress.ip_address()` 验证，支持有效 IPv4/IPv6；端口需能转整数且在 1—65535。
4. 普通文本合并连续空白，最多 300 字符；包含 `password/token/secret/private_key/access_key` 等敏感键赋值形式的值被丢弃。
5. URL/端点去掉用户凭据、查询串和 fragment；保留协议、主机、端口、路径。非标准端点也按 `?/#/@` 做有限清理。
6. `aliases` 和 `service_names` 中与节点名称相同的值，在最终紧凑格式中再去除。
7. **关系元数据只允许** `hostnames/ips/ports/endpoints/protocols/health_checks`，不会发送集群、命名空间等其他关系字段。

这些是有限白名单与清理规则，不是对所有原始日志内容的完整脱敏方案。

### 4.4 数组格式、类型和关系字典

`_compact_architecture_prompt()` 输出：

```json
{
  "ref": "sha256:<16位摘要>",
  "schema": {
    "n": ["id", "name", "t", "m?"],
    "e": ["sourceId", "targetId", "r", "m?"],
    "t": {"SV": "Service", "CL": "Cluster", "IN": "Instance"},
    "r": {"D": "DEPENDS_ON", "M": "HAS_MEMBER"},
    "m": {"ip": "ips", "p": "ports"}
  },
  "n": [
    ["API网关", "API网关", "SV", {"a": ["api-gateway"]}],
    ["Redis集群", "Redis集群", "CL"],
    ["Redis实例A", "Redis实例A", "IN", {"ip": ["192.0.2.11"], "p": [6379]}],
    ["Redis实例B", "Redis实例B", "IN", {"ip": ["192.0.2.12"], "p": [6379]}]
  ],
  "e": [
    ["API网关", "Redis集群", "D"],
    ["Redis集群", "Redis实例A", "M"],
    ["Redis集群", "Redis实例B", "M"]
  ]
}
```

这是字段形态示例，`schema.m` 为便于阅读仅列两项；实际实现放入全部 14 个元数据短键映射。`schema.t/schema.r` 只放本图用到的类型/关系。

- 没有元数据的节点/边只有三个数组元素，不补一个空对象。
- 不再逐节点发送 `layer`、完整 `kind` 字段名、`source_file`、项目内部管理字段。
- **类型语义仍以 `t` 缩写保留**，不是完全删除节点类型。
- 不发送原生 edge ID、边描述全文；节点描述转入有限的 `architecture_focus`。
- 不做拓扑子图检索来替换全图，不因候选数量少就删除其他架构节点。

内置类型缩写：`Service→SV`、`API→API`、`Component→CP`、`Database→DB`、`Cache→CA`、`Middleware→MW`、`Queue→MQ`、`Cluster→CL`、`Instance→IN`、`Host→HO`、`VM→VM`、`Pod→PD`、`NetworkSwitch→NW`、`UIControl→UI`、`UIFunction→UF`、`Function→FN`、`System→SYS`。未知类型取去掉非字母数字后的大写前 8 位，空值兜底 `CP`。

内置关系缩写：`CALLS→C`、`DEPENDS_ON→D`、`USES_DB→U`、`READS→R`、`WRITES→W`、`PUBLISHES→P`、`SUBSCRIBES→S`、`CONNECTS_TO→X`、`RUNS_ON→O`、`HOSTED_ON→H`、`HAS_MEMBER→M`、`CONTAINS→N`、`BELONGS_TO→B`、`MEMBER_OF→MO`、`ROUTES_TO→T`、`TRIGGERS→G`。未知关系保留大写前 12 位。

### 4.5 `architecture_focus` 与图谱指纹

`_architecture_focus_prompt_data()`：

1. 收集 `detail.root_service_candidate`、`analysis.resolved_root_service`。
2. 收集前 8 个算法假设的 `candidate` 及 `chain` 节点。
3. 通过目录 ID/别名索引解析成真实 ID。
4. 补充这些节点的一跳无向邻居，不是递归扩展全图。
5. 按节点 ID 排序，输出前 40 条非空描述：`{"d": [[node_id, description], ...]}`；无描述则省略此字段。

`_architecture_fingerprint()` 对规范节点/边的 ID、名称/类型、运行元数据、描述构造 JSON，使用 `ensure_ascii=False, sort_keys=True, separators=(',', ':')`，再取 SHA-256 十六进制前 16 位，加 `sha256:` 前缀。

它是快照标记，不是会话缓存开关。节点/边数组本身没有按 ID 排序，因此底层返回顺序变化也可能使指纹变化；不能把它视为严格的“忽略顺序后的拓扑等价哈希”。

## 5. 日志和其他故障信息如何进入输入 JSON

### 5.1 `incident` 字段来源

| 模型输入字段 | 数据来源 | 处理 |
|---|---|---|
| `incident_id` | `detail.incident_id`，否则 `analysis.incident_id` | 不额外概括 |
| `root_service_candidate` | `detail.root_service_candidate` | 保留日志算法的服务线索，不能等同最终根因 |
| `root_cause_candidate` | `detail.root_cause_candidate` | 保留原值；不走 `_compact_value()` |
| `root_evidence` | `detail.root_evidence` | `_compact_value()` |
| `candidate_reason_logs` | `detail.root_candidates` | `_compact_value()`，没有值时空列表 |
| `upstream_effect_logs` | `detail.upstream_effects` | `_compact_value()` |
| `fault_start/fault_end` | `detail` 同名字段 | 原时间值，不在此处改时区 |
| `observed_entities` | 证据、候选日志、影响日志及时间线 | `_extract_log_entities()`，提取 IP/端点 |
| `log_context` | `detail.timeline`，非列表按空列表 | 确定性压缩结果，或关闭压缩时的有限截取 |

完整 `detail` 并不会原样嵌入模型输入。`primary_trace_id`、窗口统计、所有顶层附加字段等未必有独立入口；某些 trace 等信息会通过关键事件或摘要间接携带。

### 5.2 通用紧凑处理 `_compact_value()`

用于根证据、候选原因日志、影响日志和部分算法候选：

| 类型 | 规则 |
|---|---|
| 递归深度 | `depth >= 4` 时返回字符串 `<truncated>`，不是继续递归 |
| 字符串 | 去首尾空白；超过 900 字符取前 899 加省略号 |
| 列表 | 前 12 项，继续递归 |
| 字典 | 按当前插入顺序取前 24 对键值，继续递归 |
| `None/bool/int/float` | 深度未超限时保留 |
| 其他对象 | 转字符串后继续上述处理 |

它不是语义摘要，不对全部字符串去掉内部换行，也不保证证据中最重要的字段总在字典前 24 项。根候选文本本身还存在不经过该函数的入口，因此不能用“每个字段最多 900 字符”概括整个请求。

### 5.3 `observed_entities` 单独保留可对齐的地址

`_extract_log_entities()` 的扫描源：

```text
detail.root_evidence
detail.root_candidates
detail.upstream_effects
detail.timeline[:120]
```

`_text_values()` 在这些值中有限递归：深度超过 3 停止；字典前 24 个值；列表前 120 项；每个字符串前 4,000 字符。提取结果：

- `ip`：IPv4 正则提取并验证，去重，最多 24 项。
- `ep`：支持若干 HTTP/Redis/MySQL/Postgres/AMQP/Kafka URL 或 `host:port` 形式，清理后去重，最多 24 项。

这条日志实体提取路径的 IPv4 正则与架构元数据验证的 IPv6 能力不同。它也不是无限扫描整条时间线。

这里的“前 120 条”只限定**模型地址线索提取**，不是前端日志异常时间线的展示截断开关，也不是压缩器的总扫描上限。

## 6. `log_context` 的确定性压缩细节

### 6.1 输入、归一化与重复模式

`_build_prompt_with_meta()` 构造以下证据对象作为权重参考：

```python
evidence = {
    "root_service_candidate": detail.get("root_service_candidate"),
    "root_cause_candidate": detail.get("root_cause_candidate"),
    "root_evidence": detail.get("root_evidence"),
}
log_context = self.log_compressor.compress(timeline, root_evidence=evidence)
```

`compress()` 只接收字典事件，并按**输入顺序**编号；此处不按时间戳重新排序。

事件消息优先级为：`root_cause → semantic_message → message → raw_block → description`，取第一个非空值，连续空白折成一个空格。不是把全部消息字段和整个堆栈拼在一起。

其他归一化包括：`level/severity` 大写、`WARNING→WARN`、服务/trace/实例字段别名兼容、消息长度限制、根因文本最多 500 字符、异常类优先 `root_exception_class`。

模式签名：

```text
service | level | (template_id 或 normalize_pattern(template 或 message))
```

`normalize_pattern()` 把时间戳、UUID、IP、长十六进制串、部分键值 ID、数字替换为占位符，转小写并压空白，最多 500 字符。此操作用于**模式分组**，不直接把 `key_events.message` 中的所有地址替换掉。

相同模式可以跨不连续的日志分组，服务与级别也是模式键的一部分。这与前端“连续且显示内容相同则折叠”的时间线 UI 规则是两套不同逻辑，不能混为一谈。

### 6.2 重要性打分

`_score_event()` 的主要加分如下：

| 项目 | 分值/规则 |
|---|---|
| 严重度 | FATAL/CRITICAL 13；ERROR 10；WARN/WARNING 6；INFO 1.5；DEBUG 0.4；TRACE 0.1；未知 1 |
| 故障关键词 | 内存耗尽 +10；死锁 +9；连接失败 +8；Redis 异常 +8；数据库异常 +8；超时 +6；上游不可用 +5；通用异常/失败 +4；重试/退避等 +2，可叠加 |
| 非空 `root_cause` | +4 |
| 非空异常类 | +3 |
| 稀有度 | `min(4, 4 / sqrt(模式出现次数))` |
| 非空 trace | +0.5 |
| 与根证据词重叠 | 每个重叠词 +1.5，最多 +6 |

关键词清单以 `_SIGNAL_RULES` 的正则为准。这是事件取舍的启发式分数，不是模型最终根因置信度。

### 6.3 选择关键事件

1. 把时间线第一项和最后一项加入优先保留集合。
2. 重复模式中最高得分达到 7 时，优先保留该模式首次/末次。
3. ERROR/FATAL/CRITICAL 或得分至少 8 的事件作为故障锚点；按分数取前 `max(4, max_events // 2)` 个。
4. 对锚点取前后 `context_radius` 个**数组邻居**，不是前后几秒钟。
5. 集合超过容量时，优先留边界和高分项，不保证所有锚点邻域都保留。
6. 尚有容量时，综合分数、新模式 +2、新服务 +1.5、新 trace +1，以及已选模式的重复惩罚补齐。
7. 最终按原始下标顺序输出，而非按分数排序输出。

### 6.4 输出结构

```text
log_context
├─ summary
│  ├─ compression_enabled
│  ├─ original_events / selected_events / omitted_events / unique_patterns
│  ├─ original_chars / output_chars / compression_ratio
│  ├─ level_counts / services / trace_ids（最多30个）
│  └─ time_range.start / end（输入首项/末项时间）
├─ key_events[]
│  ├─ order / timestamp / level / service / message
│  ├─ importance_score / selection_reasons / pattern_occurrences
│  └─ 可选 instance / trace_id / logger / template_id / root_cause /
│     exception_class / source_file / source_line
└─ repeated_patterns[]
   └─ count / first_order / last_order / first_timestamp / last_timestamp /
      level / service / template_id / representative_message
```

重复摘要只针对出现多次的模式。按 `log2(count + 1) * 2 + 严重度权重` 排序，默认前 12 个，每条代表消息最多 360 字符。摘要的 `count` 是整个模式的出现次数，可能包含已经进入 `key_events` 的事件；不能把 `count` 加到关键事件数上当作不重叠总数。

### 6.5 字符预算及降级顺序

`_fit_budget()` 只对 `log_context` 的紧凑 JSON 字符串算长度，不包含提示词、全图、根证据、候选日志等其他字段；计量单位是 Python 字符数，**不是 token，也不是 UTF-8 字节数**。

超预算依次：

1. 删掉低分的非边界事件，直到最多剩 4 项或已满足预算；不足 4 项的原输入不补齐。
2. 从末尾删除低优先级重复模式摘要。
3. 将关键消息缩短到最多 360，再每轮降 60，最低到 120；同步缩短 `root_cause`。
4. 仍然过大时，删除 `logger/source_file/source_line/selection_reasons`，限制重复模式摘要数量。

配置注释把它称为 hard budget，但当前 `_fit_budget()` 最后没有再次强制拒绝或无限裁剪。极端长字段/大摘要仍可能超预算，因此本文按实际代码称为**尽力满足的日志字符预算**，不是整个模型请求的严格上限。

`original_chars` 是归一化、消息已截短后的事件投影 JSON 长度，不是原上传文件长度。`output_chars` 是压缩器内部估算，随后 `_drop_empty()` 还会改变最终 JSON；它不是最终 HTTP 请求大小。小输入加了摘要元信息后，`compression_ratio` 可能大于 1。

### 6.6 关闭压缩不等于发送全部日志

`LOG_COMPRESSION_ENABLED=false` 时，当前请求构造逻辑取：

```python
limit = min(20, max(1, self.log_compressor.config.max_events))
key_events = [self._compact_value(item) for item in timeline[:limit]]
```

即最多前 20 项、仍做通用截断、无重复模式摘要；不是无损发送全部时间线，也不再按严重度筛选。

## 7. `algorithm_candidates` 的来源和压缩

`RootCauseEngine.analyze(detail, top_k)` 基于架构实体识别、故障信号、日志端点匹配、依赖路径/基础设施反向路径等生成 `RootCauseAnalysis`。这是本地规则和图搜索，不是第二次模型调用。

完整 `analysis` 包含 `incident_id/observed_root_service/resolved_root_service/signals/hypotheses/decision/limitations` 等字段，提示词只选：

```python
{
    "decision": analysis.get("decision"),
    "resolved_root_service": analysis.get("resolved_root_service"),
    "hypotheses": self._compact_hypotheses(analysis.get("hypotheses")),
    "limitations": self._compact_value(analysis.get("limitations") or []),
}
```

`_compact_hypotheses()` 最多保留前 8 个，每个假设只允许：

```text
rank, candidate, candidate_kind, architecture_node,
fault_mode, confidence, status, summary, chain,
evidence, missing_evidence, validation_suggestions
```

各字段再走 `_compact_value()`；`path_steps/reasons` 等未在此白名单内的字段不直接发送。`RCA_TOP_K` 默认 5、集成器限制 1—20；即使算法配置生成 20 个，模型侧仍最多看前 8 个。

提示词明确声明这些只是辅助证据，允许模型纠正候选和链路，但最终需绑定架构实体。算法和模型返回的 `confidence` 都不能直接解释成已校准的真实故障概率。

## 8. 固定提示词及最终拼接

### 8.1 固定文字包含什么

固定文字在 `_build_prompt_with_meta()` 中直接以 Python 字符串写入代码，不从单独的提示词文件加载。分为五部分：

1. 身份与数据定义：生产故障 RCA 决策助手；架构是唯一实体/关系来源；每个请求自带架构；解释紧凑数组和日志压缩字段。
2. 按优先级排列的 8 条约束，见下表。
3. 要求只返回 JSON 对象，不要 Markdown、解释或代码围栏。
4. 给出返回字段结构。
5. 补充首节点一致、缺失架构组件只能写入 `notes`，然后追加实际输入数据。

| 约束 | 实际要求 |
|---|---|
| 1 | `selected_node_id` 必须来自 `architecture_graph.n[][0]`，名称取同一行 |
| 2 | `propagation_path` 按根因 → 传播节点 → 受影响入口排列，每个 ID 必须存在 |
| 3 | 相邻路径节点须有真实直接关系；故障传播方向允许与依赖方向相反 |
| 4 | 算法候选仅为辅助，可纠正，但不得离开架构实体集合 |
| 5 | 根因依据、排查步骤、选中实体、路径必须指向同一根因 |
| 6 | `checks` 绑定真实 ID；目标字段用已有元数据；命令用地址占位符，服务端填值 |
| 7 | 只有集群级证据时不得猜成员；成员清单由服务端展开；逻辑聚合只有一个真实实例时下沉到该实例 |
| 8 | `incident_title` 是列表和详情共用的中文短标题，建议 12—40 字、最多 60 字；描述异常语义，不复制异常类全名/堆栈；不能把报错服务自动当根因；不确定要写“疑似/待确认” |

第 8 条中的空指针、Redis 示例是格式示例，不是预设诊断规则。上述是**模型指令**，不意味着服务端对每一句自然语言都能严格证明其一致性。

### 8.2 要求模型返回的 JSON

```json
{
  "incident_title": "面向用户的一句话中文故障摘要",
  "selected_node_id": "architecture_graph 中真实 node_id",
  "selected_candidate": "该 node_id 对应的真实 name",
  "selected_candidate_rank": 1,
  "selected_fault_mode": "故障模式",
  "most_likely_reasons": ["根因依据1", "根因依据2", "根因依据3"],
  "checks": [
    {
      "node_id": "真实node_id",
      "action": "排查动作",
      "target_fields": ["ip", "p"],
      "command_template": "使用占位符的可选命令",
      "expected_result": "预期结果"
    }
  ],
  "propagation_path": [
    {
      "node_id": "真实 node_id",
      "label": "面向用户的简短名称",
      "stage": "根因/故障传播/受影响入口",
      "explanation": "该节点在传播链中的作用"
    }
  ],
  "confidence": 0.0,
  "notes": ["需要补充的证据或注意点"]
}
```

### 8.3 真正的字符串拼接点

核心末尾代码为：

```python
f"输入数据：{json.dumps(self._drop_empty(prompt_data), ensure_ascii=False, separators=(',', ':'))}"
```

- `_drop_empty()` 递归删除字典中的 `None/空串/空列表/空字典`，保留数值 0 和布尔值；列表保留元素位置，不因元素为空而重排。
- `ensure_ascii=False` 让中文以中文输出。
- `separators=(',', ':')` 去掉 JSON 结构分隔符周围的空格和缩进，**不是把所有字符串中的空格/换行都删除**。
- 固定提示词仍有必要换行；字符串中的原始换行由 JSON 转义，语义仍存在。
- 返回 `(prompt, compression_summary)`。其中 `compression_summary` 由日志摘要加 `architecture.fingerprint/included/nodes/edges` 组成，单独供结果诊断，不作为 HTTP 顶层独立字段发送。

## 9. HTTP 请求体、请求头与会话

### 9.1 请求结构

`_post_conversation(prompt)` 使用 `requests.Session.post()`，不是 OpenAI SDK 的 `messages` 数组接口。

```json
{
  "content": "<第8章组装出的完整字符串>",
  "model_config_id": "<配置值>",
  "attachments": [],
  "stream": false,
  "code_language": "",
  "assistant_role": "general",
  "assistant_name": "normal_assistant",
  "assistant_prompt": "",
  "kb_id": null,
  "kb_name": null
}
```

上面展示默认形态，实际值可被部署配置覆盖。`kb_id/kb_name` 空字符串转为 `null`；有会话时另加 `conversation_id`，没有时**整个键省略**，不是传 `null` 或空串。

请求头：

```http
Content-Type: application/json
X-Ai-Coding-Key: <当前上传用户的 employee_id>
```

该链路没有另加 `Authorization: Bearer ...`，也没有把浏览器登录 token 透传给模型。`attachments=[]` 表示日志/图谱并非作为文件附件上传，它们已经进入 `content`。

`assistant_prompt` 与 `content` 是两个独立字段。远端如何合并系统提示、助手配置、知识库检索及用户内容，不在本仓库控制范围内；本文不能推断远端的优先级或最终 token 用量。

### 9.2 会话状态机

```text
新上传批次
  → new IncidentGraphIntegrator(employee_id=...)
  → new RcaDecisionService(conversation_id="", continue_conversation=True)
  → 第1次请求：无 conversation_id + 完整架构 + 当前故障日志
  → 返回非空 content，并提取 response 中的 conversation_id
  → 后续请求：已有 conversation_id + 仍然完整架构 + 下一个故障日志
新上传批次
  → 新服务对象，不继承上一批次 ID
```

细节：

- 只在返回了非空会话 ID 时更新 `self.conversation_id`；远端不返回 ID，下一次仍可能不带 ID。
- 更新发生在 `_post_conversation()` 返回前，即在模型内容被解析成业务 JSON **之前**。因此后续 JSON 解析失败，不代表该会话 ID 没有被保存。
- 会话 ID 只从响应获得，不从环境变量读取。它虽然会随决策保存到结果中，但新建批次对象不会从数据库恢复旧 ID。
- 相同对象中的会话是可变状态；当前顺序循环没有竞争，但如果未来改成并行，完整图解决的是上下文缺图问题，不等于自动解决会话 ID 更新竞争。

### 9.3 连接、超时、失败方式

- URL 默认 `http://127.0.0.1/api/conversation`，来自 `RCA_DECISION_URL`。
- 超时参数是 `(connect_timeout, read_timeout)`，默认 `(10, 90)` 秒；这是连接/读取超时，不是严格覆盖整批次的总计时器。
- `LLM_DISABLE_ENV_PROXY=true` 时 `session.trust_env=False`，不使用环境代理配置。
- HTTP 状态至少 400：抛 `RuntimeError`，错误中带响应前 1,200 字符。
- 内容为空：抛错。
- 这里没有配置自动重试，也没有“RCA 请求失败再切换 OpenAI/其他供应商”的链路；`enrich()` 返回本地算法兜底。
- `stream` 是发给远端的 JSON 字段。当前 `post()` 没有设置 requests 的 `stream=True`，返回处理不是把 token 实时推送到浏览器。

## 10. 返回文本怎样变成系统决策

### 10.1 普通 JSON 与 SSE 提取

`_conversation_content()` 先检查响应文本是否包含 `data:`：

- 不包含时，尝试 `response.json()`；依次识别 `content/response/text/message`，也支持嵌套 `data`。列表可转多行文本；无法识别的字典可能被整体序列化为文本。
- 包含时，逐行解析 `data:`，忽略无效 JSON 行，遇 `[DONE]` 结束。优先取最后一个 `message_type=chat` 的内容；否则拼接 `assistant_delta/assistant` 或无类型的内容。
- 元信息从外层/嵌套 `data` 提取 `conversation_id/execute_id/id/message_type`；最终决策主要保存会话 ID，不保存整个元信息字典。

`_parse_model_json()`：去掉 `<think>...</think>`、头尾代码围栏，截取第一个 `{` 到最后一个 `}`；先 `json.loads()`，失败再用 `json_repair.repair_json()` 修复。结果必须是字典。

### 10.2 架构约束校验与派生字段

| 处理 | 函数 | 结果 |
|---|---|---|
| 根因实体解析 | `_resolve_catalog_node_id()`、`_normalize_model_result()` | 优先 `selected_node_id/root_cause_node_id`，再尝试候选名称/别名，必要时用算法候选兜底 |
| 实例结论范围修正 | `_enforce_cluster_scope()` | 在满足父集群候选等条件时，将无实例直接证据的模型猜测退回集群；不是对所有实例结论的通用证明器 |
| 单实例聚合下沉 | `_possible_member_nodes()`、`_normalize_model_result()` | 聚合节点只展开到一个真实实例时，以该实例作为正式排查目标并添加说明 |
| 路径校验 | `_normalize_architecture_path()` | 过滤未知 ID，根因补到首位；不直接相邻但可达时，按真实图无向最短路补全中间节点；不可达则忽略该段目标并记录警告 |
| 排查步骤 | `_normalize_troubleshooting_checks()` | 最多处理前 8 个结构化步骤，只接受能绑定真实节点的步骤；目标地址从目录读取 |
| 命令呈现 | `_render_trusted_command()` | 用该节点首个 IP/主机/端口等填 `{host}/{ip}/{port}/{endpoint}/{node}`；检查部分未登记 IP、主机、端口，异常则隐藏命令并记录警告 |
| 根因条目 | `_normalize_reason_items()` | 兼容 `most_likely_reasons/reason_points` 和旧字符串字段，输出分条及拼接字符串 |
| 标题 | `normalize_incident_title()` | 标准化模型语义标题；实例范围被纠正时相应改写标题 |
| 待排查实例 | `_membership_children()`、`_possible_member_nodes()` | 正向 `HAS_MEMBER/CONTAINS`、反向 `BELONGS_TO/MEMBER_OF` 统一成父→成员；遍历真实成员、附登记 IP/端口和是否有直接日志标识 |

补充边界：

- 路径连通性校验能证明节点之间在架构中相连，不能证明“这是实际发生过的因果传播”。
- 结构化目标的地址来自图谱；自然语言 `action/reasons/notes` 不是全量事实验证结果。命令检查是有限正则检查，不是命令安全审计或自动执行授权；本链路不执行这些排查命令。
- 标准化后还会产生 `selected_node_runtime/root_scope/instance_resolution/possible_member_nodes/resolved_from_aggregate/path_validation_warnings/troubleshooting_methods/troubleshooting_checks/display_chain` 等字段，这些并非全部来自模型原始 JSON。
- `propagation_path` 与 `display_chain` 使用同一份标准化链路，供前端不同展示逻辑兼容。

### 10.3 成功与兜底包装

成功返回包含：

```text
标准化决策字段
+ source = "llm"
+ model_config_id
+ conversation_id（本次响应提取值）
+ raw_content（提取出的模型原始内容，不是完整HTTP响应）
+ log_compression（摘要，含architecture指纹与节点/边数）
```

调用/解析/标准化异常时返回算法兜底，通常 `source="fallback"`、`error` 为异常信息，并尽可能保留已计算的压缩摘要。`RCA_DECISION_ENABLED=false` 时直接返回禁用原因，不组装或发送提示词。

需要特别注意：当前没有对 HTTP 200 响应的 `retcode/code` 等业务错误码做通用成功性检查，也没有要求返回 JSON 必须具备全部决策字段。一个没有业务决策字段但能解析成字典的错误响应，有可能被字段默认值/兜底补全后仍标记 `source="llm"`。运维检查不能只看 HTTP 200 或 `source`，还要查看 `raw_content`、`selected_node_id` 和路径。本文记录此边界，不在本次文档任务中修改它。

## 11. 输入与结果存在哪里

| 数据 | 位置/字段 | 说明 |
|---|---|---|
| 原始文件 | 批次目录中的上传文件 | 不是把整个文件直接发模型 |
| 算法故障详情 | `output/incident_details.json` | 原始 `detail` 的主要来源；兼容补偿分支可能回写一致详情 |
| 整批算法摘要 | `output/summary.json`、`log_batches.summary_json` | 事件/窗口/异常数等批次摘要，不是完整模型提示词 |
| 整批 RCA 结果 | `output/rca_results.json`、`log_batches.rca_json` | 每项 `analysis.llm_decision` 保存标准化决策及成功时的原始内容/压缩信息 |
| 可读报告文件 | `output/kg_rca_report.md` | `LogFaultRunner._write_rca_artifacts()` 生成 |
| 单故障详情和分析 | SQLite `incidents.detail_json/analysis_json` | `_persist_incidents()` 保存，详情接口转换成 `detail/analysis` |
| 列表字段 | `incidents.title/root_candidate/root_confidence/fault_mode/chain_json` | 只有模型来源、根因 ID 和模型路径均满足落图条件时，根因/链路优先采用模型结果，否则回退算法 |
| 故障动态图 | HugeGraph 的 Incident、RCAHypothesis 及相关关系 | `_import_one()`、`_write_rca()` 写入，再经图谱剪枝；不是下一次请求的静态架构输入 |
| 完整发送提示词和 HTTP 请求体 | **默认不落盘** | 当前没有统一 prompt 审计文件；`raw_content` 是输出而不是输入 |

因此，`log_compression` 只能解释压缩结果的统计信息，不能直接还原全部已发送关键事件和请求正文。事后重新用数据库详情及当前图谱构建提示词，若图谱或代码已经变化，也不保证与历史请求一致。要精确回放，必须保留当时的架构快照、输入详情、算法分析、配置和代码版本，或在受控调试时捕获实际请求；不要把含工号和日志的原始请求无差别写入公开日志。

模型成功返回也不等于批次已经完成：每次模型决策之后会执行 `_import_one()` 和 `_flush_graph_buffer()`，整批图写入结束后，外层才写 `rca_results.json` 和 SQLite 故障记录。若 HugeGraph 在这期间报错，后台任务可被标为失败，即使远端已经完成推理；尚未持久化的内存决策也可能无法在页面上查看。

## 13. 无网络、无数据库的本地复现

在 `backend` 目录、项目 Python 环境中运行以下 Python 示例。它只在内存构造虚构输入，直接调用组装函数并打印结果；不调用 `enrich()`、不访问 HugeGraph、不向远端发请求，也不修改数据库。

```python
import json

service = RcaDecisionService(

architecture = {

        {"source": "API网关", "target": "Redis集群", "type": "DEPENDS_ON"},
```

## 14. 运维核查顺序与常见误解

| 症状/问题 | 首先核查 |
|---|---|
| 模型没看到某节点 | 静态快照是否读取到、项目隔离、动态过滤、ID 是否重复；再看 `log_compression.architecture.nodes/edges`，不能只看管理页总量 |
| 模型没看到 IP/端口 | 元数据是否在顶层白名单键、格式有效、是否排在前 8 项；端点/URL 是否被清理；不是所有 `meta` 都透传 |
| 模型没有看到某条关键日志 | 先看原 `detail.timeline`，再核查来源补偿限制、关键事件选择/预算、候选列表 12 项/字符串 900 字符/深度限制 |
| 关闭压缩后效果反而差 | 关闭分支只取前 20 项，不再选择中后段高分事件 |
| 为什么图谱仍有类型 | `layer` 被省略，但 `kind` 语义转换成类型短码保留 |
| 为什么请求仍很大 | 全图每次都发；12,000 只约束 `log_context` 且非绝对硬上限；其他证据入口和固定指令仍占空间 |
| 为什么 `ref` 一样仍发全图 | 指纹仅用于标识，当前代码没有按会话/指纹跳过图谱的逻辑 |
| 为什么看到 HTTP 200 但结论异常 | 检查原始内容是否为业务错误包、是否有真实根因 ID/路径；JSON 可解析不等于有效根因决策 |
| 为什么返回与原始模型 JSON 不完全一样 | 路径补全、地址绑定、集群范围修正、单实例下沉、字段兼容与兜底均发生在模型返回后 |
| 为什么有集群待排查实例却不是确定根因 | 服务端从真实成员关系展开，明确区分 `priority_check/needs_investigation`；没有证据不应断言某成员故障 |
| 为什么历史结果无法精确重放 | 默认保存结果与部分摘要，不保存完整提示词和历史架构快照 |
| 修改提示词应该改哪里 | 主规则/输入字段改 `_build_prompt_with_meta()`；图谱元数据改白名单及目录构造；日志取舍改 `LogContextCompressor`；HTTP字段改 `_post_conversation()` |

建议一次排查保留：项目 ID、批次 ID、故障 ID、代码版本、`source/error/raw_content`、`selected_node_id`、路径警告、压缩摘要和部署配置名称。工号、日志内容及拓扑地址按内部敏感数据处理，避免直接复制到外部问题单。

## 15. 与架构文档抽取、图谱剪枝的区别

- **架构文档抽取**：`LLMAnalyzer._analyze_with_conversation_http()` 使用架构抽取 `SYSTEM_PROMPT` 和文档文本，再复用 `_post_conversation()` 的传输逻辑，显式 `continue_conversation=False`；不使用本文的 `architecture_graph + incident + algorithm_candidates` 输入组合。架构抽取还存在其他适配器/兜底，不能据此推断 RCA 也有同样的模型切换策略。
- **动态图谱剪枝**：`rca_optimization.py` 的 `select_relevant_timeline/prune_pending_graph` 等作用于故障节点/边写入，调用发生在模型决策之后的集成流程，不是先剪成前端故障子图再发给模型。
- **前端图谱/时间线展示**：读取已保存的分析及图数据；前端折叠、分页、D3 布局不改变此前模型已经收到的内容。

全系统其他输入、存储与运维操作可结合 [Log系统运维SOP文档](./Log系统运维SOP文档.md) 阅读；若其历史描述与本文不同，以相应代码基线为准。
